The Family Recipe App

Dozens of double-sided recipe cards in a shoebox became a private, live, multi-user web app my family uses from their phones — running entirely on free-tier infrastructure, with AI turning a photo of a handwritten card into a structured, editable recipe in seconds.

Cloudflare PagesCloudflare Access Pages FunctionsD1 (SQLite) R2 object storageClaude API (vision) Vanilla JS PWA$0/mo infra

Screenshots use mock data — the real app is private to my family, which is rather the point. The live app sits behind Cloudflare Access: family members sign in with one tap via Google against an explicit email allow-list.

Architecture

family phones ──▶ recipes.<family-domain>.com   (Cloudflare DNS, proxied)
                    │  Cloudflare Access — Google SSO, email allow-list, JWT per request
                    ├─ static PWA shell        ← Cloudflare Pages (vanilla JS, no framework)
                    └─ /api/*                  ← Pages Function (one file)
                          ├─ recipes CRUD       → D1  · versioned edits · soft delete
                          ├─ likes              → D1  · per-user, drives "liked-by" filters
                          ├─ photo store/serve  → R2  · gated, private
                          └─ /api/transcribe    → Claude Haiku vision · photo → structured draft
Auth
Cloudflare Access in front of everything; the API validates the Access JWT signature against team public keys on every request — identity is cryptographic, never a trusted header.
Data
Recipes live in D1 (SQLite at the edge). Every edit snapshots the prior version (bounded history → "undo last edit"); deletes are soft with instant undo and a restorable trash.
AI ingestion
1–2 photos of a card (single- or double-sided) go to Claude Haiku vision with a strict transcription prompt: never invent unreadable text, mark estimated times, infer cuisine/effort. The draft opens in the same editor for human review before anything saves.
Cost engineering
Everything rides free tiers (Pages, Access ≤50 users, D1, R2). The only metered call is transcription: ~1¢ per recipe, with a family-wide daily cap enforced in D1 so a bug can never run up a bill.
Attribution
Every recipe permanently shows who added it; "edited by" appears only after someone changes it. Filters: ingredient search, total-time slider, cuisine, liked-by (AND across selected family), added-by.

The evolution

  • v1 — static & scanned: photos of each card were batch-transcribed by an AI pipeline (HEIC conversion, EXIF rotation, front/back pairing by capture order with vision verification) into markdown, compiled to JSON, hosted on GitHub Pages.
  • v2 — private & multi-user: migrated the family domain's DNS to Cloudflare without disrupting its iCloud mail (MX/SPF/DKIM inventory-first), moved hosting to Cloudflare Pages, put Cloudflare Access with Google SSO in front, added per-user likes (D1) and in-app photo uploads (R2).
  • v3 — live & editable: recipes moved from files into D1 as the single source of truth; added full in-app CRUD with review-first AI photo transcription; retired the batch pipeline entirely.

Problems worth remembering

  • Access scoping vs. fetch(): path-scoped Access apps break same-page API calls — the token mint is a cross-origin redirect fetch can't follow. One whole-host app with a single session was the fix.
  • Login UX archaeology: Cloudflare strips login_hint for its email-OTP method but honors it for Google — discovered by tracing redirect chains; it reshaped the sign-in design from "type a code" to true one-tap.
  • iPhone photo reality: HEIC decoding drops EXIF orientation, so every scanned card arrived sideways; orientation had to be re-applied manually in the pipeline.
  • Free ≠ configured: R2 and Zero Trust each need one-time manual activation that no API token can perform — worth knowing before scripting "fully automated" provisioning.
